# Audit: C# processing and managed-heap copies on the Blazor WASM main thread

Scope: per-inference / per-step / pre- and post-processing code of every pipeline the demo runs (not weight loading).
Method: static read only. Nothing was built, run or measured. Every cost below is an ESTIMATE; claims I could not read straight off the code are marked INFERRED.

Paths are relative to `D:\users\tj\Projects\SpawnDev.ILGPU.ML\SpawnDev.ILGPU.ML\`. `L` = `SpawnDev.ILGPU.ML\` (library), `D` = `SpawnDev.ILGPU.ML.Demo\`.

## Calibration (read this before trusting any number)

- Owner-measured anchors in `CLAUDE.md`: AOT vs interpreter on the TRELLIS crown = mesh simplify 2.6 s vs 41.3 s, UV atlas 0.8 s vs 16.8 s (ratio 16-21x on branchy topology code). `MeshRepair` "~5 s / 3M faces" is NATIVE only (`proj-trellis2-mesh-quality` memory). The pruned top-p scan over 152k logits is "~1 ms/token" in the interpreter (`L\Preprocessing\TextGenerationSampler.cs:90-98`), so simple float loops are far closer to AOT than topology code is (jiterpreter).
- My unit costs (INFERRED): simple numeric loop AOT 1-3 ns/element, interpreter 5-15 ns/element; hash / sort / allocation-heavy code AOT 20-100 ns/item, interpreter 16-20x that. libm call (Pow/Cos/Sin/Log) AOT ~30-60 ns, interpreter 0.1-0.3 us.
- "Per action" = one click of Generate / one photo dropped / one chat token. AOT = the deployed GitHub Pages build, INT = dev/PMT interpreted publish.
- Only the main thread exists. `Parallel.For`, `Environment.ProcessorCount > 1` branches (`MeshSimplifier.cs:19`, `SkinTokensRigger.cs:119`) are serial or dead on WASM. An `await` of an already-completed Task does NOT yield to the browser; only a real GPU await or `Task.Yield` does. So a run of synchronous host stages is ONE unresponsive block.
- The TRELLIS page already prints per-stage seconds (`Image3DPage.razor:376-383`, `_stages`). Reading those lines in the deployed build is the cheapest way to replace my estimates with facts.

### GPU-side items I noticed while reading (not CPU loops, but they decide the same user actions)

- **`GGUFGraphBuilder.EnableLastPositionLogits` is off in the browser** (`L\GGUF\GGUFGraphBuilder.cs:57`, env var `GGUF_LAST_POS=1` only). Console examples set it (`Examples\06...Program.cs:42`, `Examples\09...Program.cs:61`); nothing in `D\` does. `CaptionWriter` (`D\Services\CaptionWriter.cs:27-32`) and `AiChatPage` (`:191-201`) therefore compute lm_head logits for EVERY prompt row at prefill: ~1,000-token upsampler prompt x 151,936 vocab = a ~600 MB logits tensor and ~0.8 TFLOP, only the last row is used (`GgufGenerator.cs:357-361` reads the last row). One line in each page (`GGUFGraphBuilder.EnableLastPositionLogits = true`) removes it.
- **Per-reference VAE encoder session**: `Flux2Pipeline.EncodeReferenceAsync` builds a new `InferenceSession` from the ONNX stream for every reference (`Flux2Pipeline.cs:186`, factory at `:110-114`; same in `Flux3Pipeline.cs:84-88`), parse + graph compile + weight upload each time, up to 10 per run, because the graph is shape-fixed. Cache sessions by (h, w) for the life of the pipeline. (Weight-loading auditor may also own this.)
- **Per-step dispatch orchestration on the main thread**: `Flux3Transformer.Forward` issues roughly (5 early x 3 modes + 28 single) blocks x ~12 dispatches + dequant lookups through closures (`T(...)`, `Lin(...)`, `Flux3Transformer.cs:116-133,226-249`) every step. LLM decode already replays a recorded plan (`WebGPUDecodeCapture`); the DiT step is a fixed-shape graph apart from 3 time vectors. Use `Flux3Transformer.Profile` (`:113-125`) to see the split. INFERRED: 50-200 ms of main-thread encode per step.

## FLUX.2 details

- `Flux2Pipeline.cs:334`: `enc.Output.CopyToHostAsync()` = 512 x 7680 x 4 = 15,728,640 B (15.7 MB) read back every NEW prompt (cached afterwards, `:324`), then re-uploaded EVERY step (`Flux2Transformer.cs:115`): 4 steps x 15.7 MB = 63 MB per picture, x N seeds (`RunManyAsync` loops `:368-385`). - `GaussianNoise` (`Flux2Pipeline.cs:140-152`; used by FLUX 3 at `Flux3Pipeline.cs:187`): Box-Muller, 131,072 values = 65k pairs x (Log, Sqrt, Cos, Sin): AOT ~4 ms, INT 25-60 ms at 512 px; 4x at 1024 px (INT 0.1-0.25 s). Fix: `FlowSampler.Randn` already exists on device (`FlowSampler.cs:102-119`); note it changes the picture for a given seed (the doc comment already says the stream is not torch's).
- `ToVaeInput` (`Flux2Pipeline.cs:161-176`): 128 channels x cells, 131k scalar iterations with `/`, `%` and strided `long` writes into a 32 x 2rows x 2cols array: AOT ~3 ms, INT 10-40 ms at 512; 1024 px 524k iterations. - `EncodeReferenceAsync` token packing (`Flux2Pipeline.cs:190-203`): readback `32 x lh x lw` floats (0.9 MB at 768x576) then a 5-deep loop: ~221k elements, `(v - Mean)/Std` with 2 array lookups: AOT ~2 ms, INT 10-40 ms per reference, up to 10. Same kernel as `ToVaeInput` inverse.
- `Flux2ReferencePrep.Prepare` (`Flux2References.cs:22-44`): 3 x w x h loop, `px[s+c] / 255f * 2f - 1f`: at the demo's 768-max-side references (442k px) AOT ~3 ms, INT 15-50 ms each. `Lanczos` (`:74-98`) is NOT hit by the demo (references are shrunk to <= 768 px in `ReferenceImages.razor:93-98`, area < 1024^2) but is hit by any API caller with a larger picture: horizontal pass `h x nw x 4 x taps`; a 4000x3000 photo -> 1155x866: 3000 x 1155 x 4 x ~21 taps = 290M MACs -> AOT ~1 s, INT 15-30 s. - `DecodeTiledAsync` (`Flux2Pipeline.cs:238-286`), 1024 px = latent 128 -> starts {0, 48, 64} per axis = 9 tiles: per tile gather 131k floats (`:249-254`), `CopyToHostAsync` of 786k floats = 3.1 MB (`:257`), blend loop over 262k pixels with two `Feather` calls and 3 channel MACs each (`:260-270`); then a final pass over 1,048,576 pixels x 3 channels (`:274-284`). At 4096 px (FLUX 3 allows it, `Flux3Pipeline.cs:169`): ~121 tiles, 380 MB of tile readbacks, 270 MB of accumulators: AOT 3-5 s, INT 30-90 s and a real OOM risk on the 2 GB heap. ## Fix A (shared by many rows): get the unavoidable host topology work off the main thread
