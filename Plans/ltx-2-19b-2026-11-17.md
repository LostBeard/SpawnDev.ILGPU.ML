## RoPE, MEASURED against the dumped tables (11-17, all four 6e-8)
- Split layout: a frequency list of dim / 2 is cut per head (head h gets entries h * (D / 2) ..), and each head vector's first half pairs with its second half.
- freq_j = theta^(j / (F - 1)) * pi / 2 (float64, then float32), angle (2 frac - 1) freq_j in float32, theta 1e4.
- Video self-attn (4096 = 32 x 128): F = 4096 / 6 = 682 per axis, flattened FREQUENCY-major with the axis fastest (index j * 3 + axis), 2 entries (cos 1, sin 0)
  prepended -> 2048. Token coordinates: time midpoint of pixel frames [max(8 f - 7, 0), 8 f + 1) / fps (25) / 20; h, w: (32 h + 16) / 2048.
- Audio self-attn and audio cross (2048 = 32 x 64): F = 1024, frac = midpoint of [max(4 f - 3, 0), max(4 f + 1, 0)) x 160 / 16000 s / 20.
- Video cross (to audio, 32 x 64 heads): F = 1024 on the video token's time frac only.
- Connector (3840 = 30 x 128): F = 1920, frac = p / 4096.

## Where ComfyUI differs from diffusers' code (MEASURED 11-17 with float64 numpy references built from the taps + weights; follow ComfyUI)
- Gemma 3 RMSNorm: the scale 1 + w is formed in the weight's dtype (bf16), not fp32: fp32 leaves layer 0 2.6e-3 off, bf16(1 + w) 1.3e-7.
- DiT attention q / k RMS norms: epsilon 1e-5 (diffusers' default 1e-6): 1e-6 leaves block 0's video 1.9e-3 off, 1e-5 3e-7.
- DiT audio <-> video: v2a reads the video stream AFTER a2v's update (diffusers computes both norms first): audio 2.4e-4 -> 1.1e-7.
- Ruled out on the way (all worse): adjacent-pair RoPE, shift-first cross mods, per-head q / k norms, bf16 casts of mods / tables / temb / q, k / linear in or out /
  attention probabilities / gelu input / RoPE tables, erf GELU, Gemma eps 1e-5, relative Gemma positions.
- Dump quirk: modules that update their inputs in place (the DiT blocks) have "in" taps equal to their outputs (the hook saved after forward): use the previous
  module's output (block 0's input = patchify_proj's output).

## Speed: where a step's time goes (11-18, RTX 4070, 768 x 512 x 121 = 6144 video + 121 audio tokens; records in _TestStats)

CORRECTION first: the sampling is NOT simply disk-bound (what the 11-17 notes say). The reads run on the prefetch thread behind the GPU work.
- Two-row call (CFG recipe), files on the SATA drive: 44.0 s = GPU about 30 s + upload 8.4 s (16.2 GB a call) + read wait 5.3 s. NVMe: 38.8 s (no read wait).
- PreciseActivations off (tensor cores, bf16 activations; 5.8e-3 from the exact call): GPU about 14 s. SATA 39.7 s (then the disk bounds it), NVMe 20.9 s.
- Distilled step (one row + 6.7 GB of LoRA blocks = 22.9 GB read a step): SATA 52.4 s (disk-bound), NVMe 27.6 s, NVMe + tensor cores 18.6 s.
- Whole distilled clip: SATA 458 s, NVMe 240 s, NVMe + tensor cores 169 s. Read-ahead 2 GB on SATA: 439 s. Host cache 6 GB on SATA: 424 s.

Per-stage GPU time of one two-row call (Ltx2Transformer.StageSeconds; stages synchronized, so the sums run a little above the plain call):

| Stage (48 blocks) | precise | tensor cores |
|---|---|---|

| video ff.0 + ff.2 | 7.4 s | 5.5 s |
| video self-attention q / k / v + out projections | 3.7 s | 2.3 s |
| text cross-attention kernel | 2.8 s | 0.9 s |
| text cross-attention projections | 2.2 s | 1.4 s |

NEXT, in order of payoff for the EXACT path (TJ: speed by engineering, not by giving up quality):
1. The portable fp32 flash attention (TiledAttention): 96 attentions of 6144 x 6144 x 32 heads x 128 in 14.3 s = about 4 TFLOPS on a card whose fp32 GEMMs can
   run several times that. Profile it alone at this size (Nsight; shuffle against shared-memory variant; key-tile size; how much is the softmax's exp), then tile it
   harder. It is the kernel every backend without tensor cores runs (OpenCL, WebGPU), so the gain is not CUDA's alone.
2. An exact attention on the tensor cores (q / k / v as bf16 hi + lo pairs, like the precise GEMM): 3 to 4 MMA passes where the fast kernel takes one; bounded by
   about 3.5 x 2.4 s = 8.5 s against 14.3 s.
3. Upload: 16.2 GB a call in 6 to 9 s, serial with the compute (pageable host arrays, one stream). Page-locked staging and a second stream would overlap it.
4. Block images: each streamed load is a fresh 0.44 GB array (54 to 278 gen-2 collections a clip; 2 to 5 GB committed with a read-ahead budget): pool them.

### The portable attention kernel alone (11-18 02:10 to 02:25; Ltx2_AttentionKernels_Benchmark, self 6144 x 6144 x 32 x 128, best of 3)

- CUDA: portable (shuffle, 8 lanes x 4 queries, 8-key tiles) 139.6 ms = 4.4 TFLOPS; tensor-core flash 18.4 ms = 33.6 TFLOPS (results 2.3e-3 apart).
  NVIDIA OpenCL (the shared-memory reduction variant): 184.4 ms = 3.4 TFLOPS.
- Shape sweep on CUDA (gen_tiled_attention.py ATT_CFG = lanes, queries per thread, key tile at D 128; _tuvok-handoff/attn-sweep.ps1), twelve shapes:
  8,4,4 125.5 ms | 8,4,8 (the default) 139.6 | 8,4,2 148.1 | 8,6,4 153.2 | 8,2,8 167.1 | 16,8,4 176.0 | 8,2,4 186.5 | 8,8,8 200.0 | 8,4,1 209.6 | 16,4,4 211.7 |
  8,4,16 218.3 | 4,4,8 224.0 | 4,8,8 600.5.
- So the shape is at a local optimum; a 4-key tile is 10% better on CUDA at this size (NOT adopted: not measured at TRELLIS.2's 20k tokens, on WebGPU or OpenCL).
  More than that needs a different kernel, not a different shape. Candidates: the exact tensor-core attention (item 2 above), or finding with Nsight what holds
  this one at a sixth of the card's fp32 rate (shared-memory loads per multiply-add, the two barriers per key tile, the per-key exp).
