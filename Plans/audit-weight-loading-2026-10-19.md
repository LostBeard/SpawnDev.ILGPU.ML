## 0. What the common plumbing really does (read, with evidence)

These four facts decide most rows, so they are stated once.

A. `HubModelSource.OpenAsync` returns an `OPFSStream`, not a wrapper.
   - `LIB/Hub/HubModelSource.cs:101-107` returns `_cache.OpenOrDownloadAsync(...)`; `LIB/Hub/OpfsModelCache.cs:164-180` returns `(OPFSStream)stream` (cast at :179).
   - `OPFSStream : JSStreamBase` (`SJS:Toolbox/OPFSStream.cs:10`) and `JSStreamBase : Stream, IJSReadStream, IJSWriteStream` (`SJS:Toolbox/IJSStream.cs:5`). So it IS an `IJSReadStream`.
   - In a Window scope (the Blazor main thread) the read side is `ReadBlobStream()` (`SJS:Toolbox/OPFSStream.cs:262-266`); `BlobStream.ReadUint8ArrayAsync` is `Blob.slice -> arrayBuffer -> Uint8Array` all JS (`SJS:Toolbox/BlobStream.cs:130-139`). No .NET copy.
   - The download side (cache miss) is JS-only too: `fetch -> Uint8Array -> OPFS writable` (`LIB/Hub/HttpModelDownloader.cs:493-520` segmented `r.Bytes()`, `:621-640` streaming loop "never ReadBytes()", `:744-755` `WriteChunkAsync` uses `IJSWriteStream.WriteUint8ArrayAsync`; the `ReadBytes()` fallback at :754 is only for a non-JS store, i.e. desktop).
   - `ModelHub.OpenStreamAsync` (`LIB/Hub/ModelHub.cs:168-188`) goes through the same `OpfsModelCache`. Same type.
   - No `BufferedStream` / `SubStream` / caching wrapper exists anywhere on the browser path (grep of `: Stream` in LIB, DEMO, WebTorrent: only `FetchRangeStream`, `HttpRangeStream`, `RangeStreamModelSource.Counting`, `ModelInspectorHelper.PrefixedReadStream`, test streams).

B. `RangeStreamModelSource.OpenAsync` (`LIB/Hub/RangeStreamModelSource.cs:48-69`): cached -> `HubModelSource.OpenAsync` (OPFSStream); planned-for-cache -> same; otherwise in a browser (`OperatingSystem.IsBrowser()`, :65) it returns `FetchRangeStream` (:68), which is `IJSReadStream` (`LIB/Hub/FetchRangeStream.cs:14`, `ReadUint8ArrayAsync` :52-82, chunks are `fetch().arrayBuffer()` Uint8Arrays :120-121, spans assembled with `Uint8Array.Set` in JS :67-77). The `Counting` wrapper (:115) hides `IJSReadStream` but is returned only when NOT in a browser (:65), i.e. desktop. `HttpRangeStream` (HttpClient, managed) is used only for size probes and inspection (:64, `HubModelSource.cs:200-213`).

C. The ILGPU gate: `ILGPU:WebGPU/Backend/WebGPUMemoryBuffer.cs:227-237` takes the JS path only when `source is IJSReadStream` AND target offset, length and chunk are 4-byte multiples; everything else falls to `base.CopyFromStreamRawAsync` (managed chunk copy). The JS path is `ILGPU:IBrowserMemoryBuffer.cs:128-181` (`ReadUint8ArrayAsync` then `CopyFromJS`/`queue.writeBuffer`). Namespace check: ILGPU and ML both use `SpawnDev.SpawnJS.Toolbox.IJSReadStream`, so the type test is consistent (ML csproj pins SpawnDev.ILGPU 5.3.8, same as the source tree's `SpawnDev.ILGPU.csproj`).

D. Fail-loud guard: `InferenceSession.CreateFromOnnxStreamAsync` arms `BrowserBufferPolicy.StrictHostCopyMaxBytes = 65536` only when `stream is IJSReadStream` (`LIB/InferenceSession.cs:1627-1628`) and clears it in `finally` at :1689. It covers the MAIN weight loop (:1631-1687) only. It does NOT cover the external-data loop (:1713-1748, outside the try/finally) and is never armed for `GpuWeights`, GGUF, or any non-IJSReadStream. So for hub-path ONNX pages a single managed `CopyFromCPU` > 64 KB throws instead of silently succeeding, but any number of copies <= 64 KB is unbounded and uncounted by the guard.

## 2. VIOLATIONS, sorted by (worst-case) bytes

"Demo-reachable now?" says whether a current demo page can hit it with the files it currently loads. Where I could not tell, it says UNKNOWN and section 3 says how to measure.

### V1. GGUF: every non-quantized tensor is read into managed memory, retained, and (for F16/BF16 linear weights) streamed to the GPU a second time
- Where: `LIB/GGUF/GGUFModel.cs:77-106` (`HydrateNonQuantizedAsync`: for every tensor with `!IsQuantized(type)` it `SourceBytesAsync(...)`s the whole region into a `byte[]` held in `_regionCache`, :32/:99); `LIB/InferenceSession.cs:2233` calls it for every browser GGUF load; the dictionary lives as long as `ggufModel`, which the session keeps (`session.GgufModel = ggufModel`, :2450).
- `IsQuantized(F16/BF16/F32)` is false, so BF16/F16 LINEAR weights are hydrated too, even though `GGUFGraphBuilder.ExtractWeight` (`GGUFGraphBuilder.cs:765-787`) routes them to the native low-p stream path and `CreateFromGGUFStreamAsync` then streams them again (`InferenceSession.cs:2338-2346`). Net: a BF16/F16 GGUF is read twice and sits in the managed heap permanently.
- The non-low-p remainder is dequantised on the CPU: `ExtractWeight` falls through to `model.GetTensorFloat32` (`GGUFGraphBuilder.cs:789-794`, `GGUFModel.cs:365-393`, `ReadF32` :395-401) into a full `float[]`, uploaded by `pool.AllocatePermanent(data)` (`InferenceSession.cs:2374`) or `Allocate1D(data)` + GPU transpose (:2357-2358) = whole-tensor `CopyFromCPU` and no guard. The token-embedding table takes this path whenever it is F16/BF16/F32 (`GGUFGraphBuilder.cs:118`, tied head :572-576): e.g. a 151,936 x 2,560 embedding = 1.56 GB of `float[]`.
- Demo-reachable now? The three chat models (Q8_0) and Qwen3-4B Q4_0 should hydrate only norms/biases (INFERRED; token_embd is quantized for these, so the gather-table branch at :113-120 keeps it compressed). UNKNOWN for the unsloth Q4_0 file's non-norm F16/F32 tensors.
- Bytes: unbounded (whole file for BF16/F16 GGUF; plus 2x for lowP weights; embedding as 4 B/elem float[]).
- Fix: (1) `HydrateNonQuantizedAsync` must hydrate only tensors `BuildGraph` will consume on the CPU (1-D, below ~64 KB); skip everything routed to quantized/low-p/gather. (2) Route F32/F16/BF16 2-D weights and embedding tables through `AllocateQuantizedBytesFromStreamAsync` as raw typed bytes and do the F16/BF16->F32 widen and the [N][K]->[K][N] transpose on the GPU (the F16/BF16 lowP branch already does the transpose natively, `InferenceSession.cs:2338-2347`); extend lowP to the embedding gather and tied head. (3) Drop `_regionCache` after `BuildGraph`.

### V2. `CreateFromHuggingFaceAsync` external-data fallback drains the whole model AND the whole `.onnx_data` into byte[]
- Where: `LIB/InferenceSession.cs:1010-1046`. When the probe at :991 sees external data, control falls out of the `await using` block and runs `hub.LoadAsync` (:1011, `[Obsolete]`, `ModelHub.cs:99-139`: `OpenOrDownloadAsync -> MemoryStream.CopyToAsync -> ms.ToArray()` = 2 copies) for the model and again for the data (:1034), then `ResolveExternalData` (:1038) + `CreateFromOnnxParsed` (:1042) / `CreateFromFile` (:1046) -> `AllocatePermanentChunked`.
- Demo-reachable now? No current page loads an external-data ONNX through this helper (all file sizes are single-file; INFERRED from repo layouts, UNKNOWN for each hub file - `HasExternalData` decides at runtime). It is the documented helper (`GettingStartedPage.razor:67-69`), and DAv3/Parakeet/most onnx-community exports are external-data.
- Bytes: about 2 x (model + data) transient plus the retained `bytes`; > 256 MB total OOMs the tab.
- Fix: the streaming loader already supports it: open `hubStream` for the model and `hub.OpenStreamAsync(repo, dataFilename)` for the data and call `CreateFromOnnxStreamAsync(..., externalDataStream: dataStream)` (`InferenceSession.cs:1466, 1713-1748`). Delete the byte[] fallback; if OPFS is unavailable throw.

### V3. ONNX stream parser materialises bf16 / fp8 / uint8 / int / bool initializers (> 64 elements); the bf16/fp8 streaming code in BufferPool is unreachable from it
- Where: `LIB/Onnx/OnnxParser.Stream.cs:236-246`: only `DataType == 1 || 10 || 3` (fp32, fp16, int8) with > 64 elements get `RawDataStreamOffset`; everything else does `tensor.RawData = await r.ReadBytesAsync(rawLen)` (:245). `BufferPool.AllocatePermanentFromStreamAsync` claims dtypes 16/17/18/19/20 (`BufferPool.cs:1330-1394`) but the parser never hands them a stream offset, so they take `InferenceSession.cs:1674 -> AllocatePermanentChunked` (`BufferPool.cs:1187-1264`): `byte[]` + `ToFloatArray()` expansion + 1 MB-chunk `CopyFromCPU`. Same for uint8 quantised weights (dtype 2), int32/int64/bool tensors, and for any `Constant` node whose `value` tensor is large (node bytes are read whole: `OnnxParser.Stream.cs:84-90`; uploaded via `StreamTensorsFromParsed`, `OnnxLoader.cs:154-171`).
- Demo-reachable now? UNKNOWN. A bf16/uint8 model or a GPT-2 style 1,024x1,024 BOOL mask initializer would hit it; with the guard armed (D) it throws with a tensor name rather than copying silently. `TextGenPage` (distilgpt2, optimizer off) is the page most likely to expose it.
- Bytes: size of each such tensor (4 B/elem after widening).
- Fix: in the parser, record the stream offset for dtypes 16/17/18/19/20/2 as well (the loader branch exists); add GPU cast kernels for int32/int64/bool/uint8 (the comment at `BufferPool.cs:1325-1329` says uint8 is blocked on an ILGPU signed-convert lowering bug: fix it in ILGPU per Rule 2); stream Constant-node tensors the same way.

### V4. Gemma 4 multimodal (library only): mmproj read whole, dequantised on the CPU, uploaded as single copies
- Where: `LIB/Pipelines/Gemma4MultimodalPipeline.cs:165-167` (`MemoryStream` + `ToArray()` + `MmprojModel.Load(bytes)`), `LIB/GGUF/MmprojModel.cs:32-39` (`GGUFParser.Parse(bytes)`, whole file resident), `LIB/GGUF/Gemma4ProjectorWeights.cs:50-62` (`GetTensorF32` -> float[] for every projector tensor), `LIB/GGUF/Gemma4MultimodalProjectorGpu.cs:86` (`accel.Allocate1D(a)` = whole-tensor `CopyFromCPU`, no guard).
- Bytes (computed from the tensor shapes documented in `MmprojModel.cs:7-21`, INFERRED sizes): file ~167 MB x3 copies (stream -> MemoryStream -> ToArray -> parse), plus float[] of patch_embd 6912x3840 = 106.2 MB, mm.input_projection 3840^2 = 59.0 MB, position_embd 3840x1120x2 = 34.4 MB, audio 640x3840 = 9.8 MB = 209.4 MB, each uploaded in ONE copy.
- Demo-reachable now? No page (tests only: `MLTestBase.Gemma4ProjectorGpuTests.cs`).
- Fix: stream the 2 bf16 matrices through `AllocateQuantizedBytesFromStreamAsync` + a GPU bf16->f32 (or keep bf16 and use the low-p matmul); read only the few small tensors (norms, biases) to the host.

### V5. ZipVoice vocoder, 54,157,409 B, downloaded with HttpClient into a byte[] (DEMO page, reachable)
- Where: `DEMO/Pages/TextToSpeechPage.razor:397-422`: `Http.GetAsync(warmUrl)` (:406, buffered `GetAsync`), then `InferenceSession.DownloadBytesChunkedAsync(Http, memberUrl)` (:418, `InferenceSession.cs:3195-3290`: HttpClient response stream -> 1 MB buffer -> `byte[contentLength]`), then `CreateFromFile(_accelerator!, bytes)` (:421) -> `CreateFromOnnx` -> chunked `CopyFromCPU`. Guard is not armed (byte[] path).
- Bytes: 54.2 MB byte[] resident + 1 MB read buffer + one fresh `float[]` chunk per MB uploaded = about 2x model of managed traffic, 54 MB resident, on the Clone path.
- Fix: the hub URL is just a URL: `OpfsModelCache.OpenOrDownloadAsync(memberUrl, cacheKey)` (`OpfsModelCache.cs:164`) already caches an arbitrary URL into OPFS without touching the heap; then `CreateFromOnnxStreamAsync(stream)`. Also replace the `GetAsync(warmUrl)` poll with `ResponseHeadersRead` (or `fetch`) so a 200 body is never buffered (UNKNOWN what the hub returns, section 3).

### V6. YOLOv8n, 12,823,637 B, HttpClient byte[] (DEMO page, reachable)
- Where: `DEMO/Pages/DetectPage.razor:310` (`Http.GetByteArrayAsync`), :318 `InferenceSession.CreateFromFile(bytes)`.
- Bytes: 12.8 MB x >= 3 as in V5 (HttpClient's own buffer, the byte[], per-chunk float[] copies).
- Fix: same as V5: serve it through `HubModelSource`/`OpfsModelCache` (the page already says it wants the bundled copy: call `OpfsModelCache.OpenOrDownloadAsync(new Uri(Http.BaseAddress, "models/yolov8n/model.onnx").ToString(), key)`) and `CreateFromOnnxStreamAsync`. BlazeFace (`FaceDetectPage.razor:289`, 229,746 B) is under the 1 MB threshold but is the same pattern; move it with the same helper so the page stops being a counter-example.

### V7. ILGPU 4-byte gate sends a WHOLE tensor through the managed heap when its byte length is not a multiple of 4 (library fix, Rule 2)
- Where: `ILGPU:WebGPU/Backend/WebGPUMemoryBuffer.cs:227-237`: the condition is on the total `lengthInBytes & 3`, not on the tail. `BufferPool.AllocateQuantizedBytesFromStreamAsync` calls `buffer.View.SubView(0, byteLength).CopyFromStreamAsync(...)` with the unpadded `byteLength` (`BufferPool.cs:1650-1671`), and its own comment says "an odd-length tail gracefully falls back to the managed read" - but the fallback is per CALL, so a Q8_0/Q4_0/Q5_0 tensor with an odd number of 34/18/22-byte blocks, or a Q6_K one with an odd number of 210-byte blocks, goes entirely managed (up to hundreds of MB). Same for `GpuWeights.UploadAsync` (`GpuWeights.cs:147` explicit `bytes % 4` test, then the managed loop :152-160) and odd-count fp16/int8 ONNX tensors (`BufferPool.cs:1365`, ILGPU doc `WebGPUMemoryBuffer.cs:215-219`).
- Demo-reachable now? By arithmetic the demo GGUF files are aligned: Q8_0 rows are K/32 x 34 B with K/32 even for K = 896, 960, 640, 4864, 2560, 2048 (all of Qwen2.5-0.5B, SmolLM2-360M, Gemma3-270M); Q4_0 (18 B) with 80 and 304 blocks per row, Q4_1 (20 B), Q6_K (210 B x 10 / 38 blocks) for Qwen3-4B are all multiples of 4. So INFERRED safe, not measured. It will bite other models.
- Bytes: whole tensor (up to the 2 GB single-tensor limit the code asserts at `GGUFGraphBuilder.cs:735`).
- Fix (ILGPU): upload the 4-aligned prefix on the JS path and only the <= 3-byte remainder through a padded 4-byte `writeBuffer`; the destination buffers are already padded (`BufferPool.cs:1650-1651`). Then `GpuWeights` and the BufferPool callers need no special case.

### V8. `DepthEstimationPipeline.CreateFromHubAsync` default path reads model.onnx whole and streams it from a MemoryStream (library only)
- Where: `LIB/Pipelines/DepthEstimationPipeline.cs:399-400` (`FetchBytesAsync` -> `new MemoryStream(modelBytes)`), so the structure stream is not an `IJSReadStream`: the guard (D) is not armed and any initializer stored inline in model.onnx is read through `CopyFromStreamAsync(MemoryStream)` = managed. The default `externalDataFile = "onnx/model.onnx_data"` (:380) also sends a single-file repo down this path (it relies on callers passing `""`).
- Bytes: size of model.onnx (DAv3 structure file is small INFERRED; a single-file model would be fully managed).
- Fix: stream model.onnx from `source.OpenAsync` as the else branch does (:416); `ParseFromStreamAsync` already works on it.

### V9. RNN / GRU (always) and LSTM (fallback) read their weights back from the GPU into managed float[] and cache them for the life of the operator
- Where: `LIB/Operators/RecurrentOperators.cs:37, 40, 57-63` (RNN), `:230-233, 262-267` (LSTM, host fallback after `TryExecuteOnAccelerator` at :257 fails), `:629-632, 649-655` (GRU); `LIB/Operators/OperatorInputReader.cs:59-70` (`staging.CopyToHostAsync<float>` = `WebGPUMemoryBuffer.CopyToRawAsync` -> `u8.ReadBytes()` -> byte[] -> float[], `ILGPU:WebGPU/Backend/WebGPUMemoryBuffer.cs:195-207`) and `ReadCachedAsync` (:98-107).
- Demo-reachable now? Kokoro's LSTMs take the accelerator path (layout 0, 3-D X, `RecurrentOperators.cs:307-320`) so no W/R readback is expected (INFERRED); no demo model contains GRU/RNN. A GRU/RNN model, or an LSTM with `layout=1`, would read W, R, B to the host and keep them.
- Bytes: |W| + |R| + |B| per layer (Kokoro-class bidirectional 512/256 LSTM would be ~6 MB per layer INFERRED).
- Fix: add GPU kernels for GRU/RNN like `RecurrentKernels` has for LSTM; never cache weight readbacks.

### V10. Inspector page: a LOCAL file is read-and-discard through the managed heap
- Where: `DEMO/Pages/InspectorPage.razor:292-293` (`file.OpenReadStream(...)` is a forward-only Blazor stream) -> `ModelInspectorHelper` ONNX branch (`LIB/Onnx/ModelInspectorHelper.cs:104-114`, "a forward stream ... reads-and-discards weights") -> `StreamProtoReader.SkipAsync` read loop (`LIB/Onnx/StreamProtoReader.cs:134-140`). SafeTensors/GGUF are header-only. Non-ONNX/GGUF/SafeTensors formats are drained whole (`ModelInspectorHelper.cs:120, 245-250`).
- Not a GPU load, but every weight byte of the user's file crosses JS->.NET once, transiently. Hub inspection (`HubModelSource.OpenForInspectionAsync`, :200-213) is fine: it Seeks over weights and exposes `BytesFetched` for assertion.
- Fix: for a user file use `Blob`/`File` as a `BlobStream` (an `IJSReadStream` with `Seek`, `SJS:Toolbox/BlobStream.cs`), which makes the inspector's Seek branch available and reads only the structure.

### V11. Whole-file managed reads that are allowed or desktop-only, listed so they are not mistaken for clean

### V12. `GpuWeights.LoadAsync`: unconditional 16 MiB scratch plus a managed fallback for odd-sized tensors
- `LIB/Trellis2/GpuWeights.cs:107` allocates `new byte[16 << 20]` on every load (7 TRELLIS checkpoints, 2 per FLUX.2/FLUX 3 stage pair, SkinTokens) even though it is used only for non-seekable gap skipping (:115) and the odd-size fallback (:152-160). WASM linear memory never shrinks, so each of these is a 16 MiB high-water bump (LOH, zero-filled). Fix: allocate lazily at first use.
- Tensors with `bytes % 4 != 0` (odd-count bf16/f16 vectors) go `ReadExactlyAsync -> Cast -> CopyFromCPU` (:152-160). Expected tiny; no census guards it (the guard in D is not armed for `GpuWeights`). Fix: V7 in ILGPU, or arm `StrictHostCopyMaxBytes` around `GpuWeights.LoadAsync` the way `CreateFromOnnxStreamAsync` does.

### V13. Weights loaded more than once
- Whisper: `decoder_model.onnx` and `decoder_with_past_model.onnx` are both loaded (`WhisperPage.razor:203-217`) and both contain the decoder weights; the pipeline keeps both sessions (`:231`). Duplicate OPFS download and duplicate GPU residency (size INFERRED ~100 MB of the 226 MB doc total). Fix: use only the merged decoder (`decoder_model_merged.onnx`) with the `use_cache_branch` input, as the file `KnownFiles.OnnxDecoderModelMerged` (`ModelHub.cs:458`) anticipates.
- FLUX.2 / FLUX 3 reference images: `VaeEncoderFactory` opens `vae_encoder.onnx` and builds a fresh `InferenceSession` PER reference picture (`Flux2Pipeline.cs:110-114`, `Flux3Pipeline.cs:84-88`, called from `EncodeReferenceAsync`), up to `MaxReferences = 10` times. JS->GPU each time (no heap cost) but 10x the upload; the graph is fixed-shape, so cache by (h, w).
- FLUX text encoder is re-streamed per new caption by design (`Flux3Pipeline.cs:152-161`); TRELLIS streamed files are re-fetched every run when the browser cannot cache them (`Image3DPage.razor:312-331`). By design; not heap.
- `CreateFromHuggingFaceAsync` parses the ONNX structure twice per load (probe at `InferenceSession.cs:991`, then again at :1474 inside `CreateFromOnnxStreamAsync`).
- Pages each construct their own `new ModelHub(JS)` (e.g. `ClipPage.razor:138`), bypassing the shared singleton whose per-key download gate `Program.cs:38-51` says must be shared; two pages can race one OPFS entry.

### V14. Guard / census coverage gaps (why a regression would not be caught)
- Guard armed only for `IJSReadStream` ONNX main loop (`InferenceSession.cs:1627-1689`); not for external-data (:1713-1748), GGUF, `GpuWeights`, Gemma4, or `CreateFromHuggingFaceAsync` fall-backs.
- Only one test asserts the census: `MLTestBase.Flux3Tests.cs:313-341` (`HostCopyBytes < 4 MiB`). No such assertion exists for FLUX.2, TRELLIS.2, SkinTokens, SD Turbo, RMBG, CLIP, Whisper, Kokoro, ZipVoice or GGUF chat. Writing one per model from that template turns "read the code" into a regression gate.
- `StrictHostCopyMaxBytes` is a process-global that `CreateFromOnnxStreamAsync` sets to 65536 and resets to -1 in `finally` (:1628, :1689): it clobbers a caller's own setting and races with a concurrent load.

## 4. Verified clean (read the code that proves it)

- Hub download and cache: fetch -> `Uint8Array` -> OPFS, no `ReadBytes()` on the payload path (`HttpModelDownloader.cs:493-520, 621-640, 744-755`; `OpfsModelCache.cs:6-39`).
- `OPFSStream` / `FetchRangeStream` implement `IJSReadStream`; no wrapper hides it in a browser (section 0).
- ONNX stream loader, fp32 / fp16 / int8 with > 64 elements and an even byte count: JS->GPU via `CopyFromStreamAsync` (`BufferPool.cs:1348-1354, 1364-1394, 1577-1603`), widened/narrowed on the GPU (`StreamLowPUpcastAsync` :1447-1457).
- GGUF quantized tensors: JS->GPU raw bytes, decoded in-register (`BufferPool.cs:1638-1673`); the embedding stays compressed for gather AND tied head with a single deduped upload (`GGUFGraphBuilder.cs:565-571`, `InferenceSession.cs:2313-2330`).
- Safetensors `GpuWeights`: native dtype upload, no conversion (`GpuWeights.cs:121-124, 149`); DINOv3 f32 -> f16 conversion is a GPU kernel (`DinoV3Extractor.cs:~95-130`); FLUX quantised blocks are dequantised on the GPU just before each GEMM (`Flux2Weights.cs:56-63`).
- Kimodo / animation: no network weights at all.
- Optimizer-folded constants uploaded by `UploadOptimizerFoldedInitializers` (`GraphExecutor.cs:5734-5760`) are shape-arithmetic values from `FoldConstants` (`GraphOptimizer.cs:1816+`), not weights.
- `PromptMatchScorer.CreateAsync` streams CLIP (`PromptMatchScorer.cs:20-26`).
- Whisper mel filterbank is a computed constant uploaded once: 80 x 201 floats = 64,320 B (`Preprocessing/WhisperMelPreprocessor.cs:205-210`), 1,216 B under 64 KiB; not a weight.

## 5. Related bulk traffic that is NOT weights (listed because it breaks "zero-copy is law", fix separately)

- FLUX.2 text conditioning is read back to the host and re-uploaded every step: `enc.Output.CopyToHostAsync()` (`Flux2Pipeline.cs:334`) = 512 x 7,680 x 4 = 15.7 MB (two managed copies on readback), then `Forward(..., embeds, ...)` -> `CopyFromCPU` of the same 15.7 MB each of the 4 steps (`Flux2Transformer.cs:115`, `Flux2Pipeline.cs:375`), plus per-step RoPE tables (:118) and the prediction readback (`Flux2Pipeline.cs:377`). FLUX 3: caption rows `[tokens, 20,480]` read back (`Flux3Pipeline.cs:160`, 6.5 MB at 80 tokens) and uploaded once (`Flux3Transformer.cs:171`). Fix: keep the encoder output buffer alive on the GPU and copy buffer-to-buffer (`CopyFrom`) into the transformer input; compute RoPE tables with a kernel (the DINOv3 path already does, `DinoV3Extractor.cs:~170`).
- FLUX VAE tiled decode accumulates `float[3*H*W]` on the host (`Flux2Pipeline.cs:242`).

## 6. Summary by severity

Demo-reachable and confirmed managed-heap weight loads: V5 (54.2 MB vocoder), V6 (12.8 MB YOLOv8n), plus tiny BlazeFace and the Inspector local-file path. Latent but real library defects that would take whole models through the heap on files the demo does not use today: V1 (GGUF non-quantized), V2 (external-data ONNX), V3 (bf16/fp8/uint8/int/BOOL initializers), V7 (4-byte gate), V4 (Gemma4 mmproj), V8, V9. All large-model demo paths (FLUX.2, FLUX 3, TRELLIS.2, SkinTokens, SD Turbo, RMBG, CLIP, Whisper, Kokoro, ZipVoice enc/dec, Depth, GGUF chat) are JS->GPU by construction, subject to the unmeasured items in section 3.
